Where checkpoint 280 lost its solve rate, and how stage 8 got it back

Checkpoint 280 solves 13 points fewer stage-5 problems than checkpoint 220. Evaluating every checkpoint in between shows the loss sits in the first 20 steps of stage 7, as the model stops re-running its code before it submits. The first 40 steps of stage 8 bring both the solve rate and the checking back.

What this says

  • Stage 7's early steps did most of the damage. Solve rate falls 3.9 pp from 240 to 250 and 6.1 pp from 250 to 260, then stays put. Stage 7's training reward reached its ceiling around step 250 (every group all-good), so the later steps had almost no signal to push the behaviour either way.
  • Stage 6 started the shortening. From 220 to 240, reasoning drops 15% (−1.5k characters, CI −1.9k to −1.0k) and wrong answers double (5.9% → 12.6%). The solve rate barely moves (−2.0 pp, CI −4.2 to +0.1) because empty submissions fall by about the same amount.
  • Stage 7 removed the final check. The share of episodes that run the code after the last edit falls from 84% at 240 to 63% at 260 and 55% at 280. Wrong answers keep climbing to 25%, and 81 of 280's 200 wrong answers fail the very first hidden test.
  • This is a real regression, not a reshuffle. On the 300 stage-5 rows that 220 solves in both samples, 280 fails 16% of episodes. 64 of those 98 failures are wrong answers and 29 are timeouts.
  • It isn't specific to the stage-5 env. test_cases_hack, which every checkpoint trained on equally in stage 2, follows the same shape: 85.5% → 77.0%, with the change landing in stage 7.
  • Stage 8 undoes it within about 30 steps. Stage-5 solve rate climbs 67.2% → 71.4% → 76.0% → 77.1% across 290–320, level with 220 (−0.7 pp, CI −3.2 to +1.9). Re-running the code after the last edit returns to 85% and reasoning to 9.6k characters. test_cases_hack is back to 85.5%.
  • The recovery is close but not exact. Wrong answers are still 4.4 pp above 220 (CI +1.9 to +7.1), and 4.2% of the rows 220 always solves still fail. Since the behaviour comes back once checking pays again, stage 7 most likely taught a short-episode habit rather than removing capability.
Correction

An earlier count in this investigation said checkpoint 280 still re-ran its code before submitting (82% vs 86% at 220). That was wrong: the count treated the #!/usr/bin/env python3 line, which 280 often writes at the top of its solution, as a run. Counting only python/pytest outside heredoc bodies gives 55% at 280. The figures on this page use the corrected count.

Method

  • Checkpoints: Tinker sampler weights 180 and 220 (stages 4–5), 240 (end of stage 6, run 49582a3a), 250 / 260 / 270 / 280 (stage 7, run 9c73ab94), and 290 / 300 / 310 / 320 (stage 8's first 40 steps, run 0dd5a127).
  • Harness: baseline/rollout.py at training settings (temperature 1.0, 6k tokens per turn, 8k per trajectory, 30 turns, no tool-call repair), on the host's SandboxFusion containers with off-loop grading. 11,000 episodes across all checkpoints, 0 errors.
  • Paired differences: per-task mean at each checkpoint, bootstrapped over tasks (2,000 resamples).
  • Code: experiments/control_reward_seeker/baseline/ckpt_decoy/ on branch worktree-ckpt-drop-bisect (run_bisect.sh, run_stage8.sh, drop_trace.py, output in drop_trace.txt).
